# 文体と見せ方の決め（指摘の蓄積）

著者が執筆中に出した指摘を、次の記事で先回りするためのメモ。フェーズ 5（執筆）の整形とフェーズ 6（校正）で、書く前に読む。
新しい指摘が出たら、ここに 1 行足す。チームで使うなら、合わないものは消してよい。

## 文体

- **です・ます で統一**。口述が だ・である でも です・ます に整える。引用の中は原文のまま
- **口語寄り**。「〜なんだろう？と思って調べてみました」くらいの温度。硬い書き言葉にしない
- **くどい締めを付けない**。「この記事で言いたいのは〜ということです」「〜だったのです」は削る。言いたいことは TL;DR と本文で言う
- **断定しない**。「〜は動かない」→「〜のケースでは動かないことが多い」。根拠の無い言い切りは書かない
- 推測を書くときは「推測ですが」と明記し、直後に数字の根拠を置く
- 進行実況（「ここまでで〜は分かりました。次に〜を押さえます」）は書かない。節の頭は反問で開く（「では、ここまで設定すれば黙っていても通知は来るのでしょうか」）
- 「まとめると、理由は「A」「B」「C」のどれか」のように鉤括弧を並べない。箇条書きにする
- 導入（節 0）は 2 段落まで。誰向けか 1 文、何があって何を調べたか 1〜2 文。手順の細かい予告はしない
- TL;DR は事実の列挙にせず、「これがこうなって、最後はこうした」の流れで 3 行
- TL;DR は、その分野に詳しくないエンジニアでも読める言葉で書く。専門語や雑な略は、何をするものかの言い方に開く
- 専門用語は初出で何をするものかを括弧で開く。ただしカッコの注釈を重ねない。略語や識別子の言い換えを括弧で足すのは控え、要るものだけ残す
- 読者のエンジニアにとって当たり前のことは厚く説明しない。補足が要るなら 1 文と原典のリンクか、details に
- 選んだ理由は「背景の説明 → だからこれにした」の順に書く。結論の文のあとに理由の段落を足さない
- 同じ説明を 2 回書かない。最初の 1 回だけ
- 「（〜の出力は〜の抜粋）」「（パスは手元のリポジトリのもの）」のような機械っぽい注記は書かない
- カタカナの製品用語は製品の表記に寄せて統一する（画面のボタン名だけは画面の表記のまま）
- 他の人が作った OSS に触れるときは敬意のある言い方にする

## 引用と根拠

- **本文に英文引用を重ねない**。本文は日本語の要点（箇条書き）＋ドキュメントへのリンク。原文は `:::details 公式ドキュメントの原文` に英文＋（日本語訳）＋出典リンクで置く
- 訳は主語を補った完全な文にする。エラー文は「画面に表示されるエラー文」のように何の文か明記する
- 英文を引用するなら、リンク先も英語ページ。本文側のリンクは日本語ページでよい
- 根拠は **計測と文献の両方**。ただし分量は増やさない（箇条書き 2 行、表は 3 行まで）
- 「どこで分かる？」と聞かれたら、推測で答えず API やコマンドを叩き直す。分からないことは「外からは分からない」と本文に書く
- 論文を引くときは節番号と表番号まで書く（「4.2 節」「Table 3」のように）
- 製品・ライブラリ・規格・ツールは、本文（または用語の表）の初出に原典のリンクを付ける。リンクは全部 200 を確かめる
- 使った OSS の中身（相手側の話）は記事に載せない。自分がやったことに関係する部分だけ
- 本題でない説明（API のレート制限など）は、再現性評価で指摘されても入れない

## 見せ方

- **TL;DR を導入の直後に 3 行**。簡潔に、読者が場面を想像できる言い方で
- 用語は本文の括弧で重ねず、TL;DR の直後に **2 列の表（用語／意味）**。`:::message` は注意アイコンが付いて警告に見えるので用語には使わない
- 画像は「上の文の説明」と分かるように、**説明の文 → 画像 → `<br>`** の順。画像にラベル（画面 1、画面 2）は付けない。1 枚目は「タイトル部分だけ」など、高さを指定して小さく撮る（`shot.sh <url> <out> 1280 400`）
- 全部 ❌ になる表のように、情報量の無い表は作らない。箇条書き＋メッセージ枠 1 つで足りる
- GUI で確かめられることは GUI（スクリーンショット）を主にし、コマンドは `:::details コマンドで確かめる場合` に。ただし手順として打つコマンド（起動・ビルド）は折りたたまず、本文に置く。画像があるなら画像のすぐ上
- 「載っていない」を示したら、**載っている場合の画面も比較で置く**
- 図は mermaid の **sequenceDiagram**（縦線 4 本まで。5 本だと文字が小さい）。番号 ①〜⑤ を本文で参照する。強調は `rect rgba(220, 53, 53, 0.4)`（薄い rgb はダーク背景で消える）。図の形は候補を 3〜5 案並べて著者に選ばせる
- sequenceDiagram は下側の名前の箱を消す（先頭に `%%{init: {"sequence": {"mirrorActors": false}}}%%`）。本文で触れる機器や登場人物を図から落とさない
- 長い出力（ファイル一覧など）は要点を本文に書き、全体は details へ。details の題に「コラム」「補足」のような前置きは付けない。題は中身の問いにする
- 記事のコード（yaml・Dockerfile・スクリプト）は、全体版を公開リポジトリに置いてリンクする。コードのパスは公開リポジトリの構成に合わせる。画像を撮るためだけの設定は、記事と公開リポジトリのコードに入れない
- 他者のソフトの画面を載せるときは、README などの但し書き（画像の二次利用の禁止など）を先に確かめる。載せるなら使う部分だけを切り出し、画像の下に出所のキャプション（`*画面: …*`）を付ける
- Zenn のタイトルは 70 字以内（プレビューが警告を出す）

## 進め方

- プレビューを開いたら、**確認依頼で本文を貼らない**。変更点だけ言う。著者はブラウザで見ている
- 著者から口述が無いとき（「任せる」「次進んで」）は、brief と outline と原典だけで書き、「著者の言葉は入っていない」と記録に残す
- 著者が「下書きを作って、それを私が直す形」を望んだら、全節の見出しを入れた下書きを先に作り、判断が要る所は TODO にして著者に直してもらう
- 口述の文はそのまま使う。言い換えが要るときは案を出して著者に選ばせる
- 著者が「スマートに」と言ったら、文を削る方向。足さない
- 図を直した結果は、著者が実機（スマホなど）で見て判断する。内蔵ブラウザのプレビューで mermaid が「Syntax error」になることがあるが、記法が mermaid 単体で通るなら環境の不調。切り分けに時間をかけない
